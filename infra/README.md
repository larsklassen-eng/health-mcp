# Infrastructure (AWS)

Terraform for the Factored AWS sandbox account (`us-east-1`). One deployment, `rag`, deployed
from `main`: its image repositories, secrets, app server and its public URL (CloudFront). The
configuration supports one independent deployment per branch, should another one be needed.

## Deployments

| Deployment (workspace) | Branch | State in S3 | Resource names |
|---|---|---|---|
| `rag` | `main` | `health-mcp/rag/terraform.tfstate` | `health-mcp-rag-*` |

The deployment is called `rag` because this code used to live on the `rag-option-a` branch, which
became `main` on 2026-11-12. Renaming it would recreate every resource (and its data disk), so the
name stays.

The Terraform workspace picks the deployment. Each one has its own state, its own resources
(named with `local.name_prefix` and tagged with `deployment`) and, once the app is deployed, its
own URL, database, secrets and login, so access to one never gives access to the other. Nothing
is shared between them except the account's VPC. The default workspace is refused, and the
deployments are listed in `environments/sandbox.tfvars`.

Apply the `rag` deployment from `main`, the branch it runs.

| File | What it holds |
|---|---|
| `versions.tf` | Terraform and AWS provider versions; the S3 backend |
| `providers.tf` | AWS provider: credentials from the environment, tags every resource |
| `variables.tf` | Inputs: account settings, VPC and subnets |
| `network.tf` | Looks up the existing VPC and subnets (they are not managed here); the deployment's name prefix |
| `registry.tf` | ECR repositories for the three images (`health-mcp-<deployment>-api`, `-mcp-server`, `-web`), keeping the last 10 images each |
| `server.tf` | The app server: a `t4g.small` (ARM) in a private subnet, its IAM role (with the permissions boundary), security group, and a separate encrypted data disk |
| `server/` | What runs on the server: the boot script (Docker, Compose, swap, data disk, systemd service), the Compose file, `deploy.sh` and `monitoring.sh` (Phoenix) |
| `cdn.tf` | The public URL: a CloudFront distribution reaching the server through a VPC origin, and the security group rule that lets CloudFront in |
| `secrets.tf` | SSM parameters under `/health-mcp/<deployment>/`: `MCP_AUTH_TOKEN`, `SESSION_SECRET` and `PHOENIX_API_KEY` (generated), `OPENROUTER_API_KEY` (set by hand), and Phoenix's own secrets under `phoenix/` (generated) |
| `outputs.tf` | The deployment, the VPC's CIDR, each subnet's availability zone and CIDR, the image repositories, the secret names, the app's URL and the server's files for the rollout |
| `environments/sandbox.tfvars` | The sandbox account's values and the deployments |
| `environments/sandbox.s3.tfbackend` | Where the state lives: S3 (one file per deployment), encrypted with KMS, locked by S3 |

## The sandbox account

- **Deployer role:** `health-mcp-deployer`. Only GitHub Actions in `factoredai/health-mcp` can
  use it (its trust policy allows GitHub's OIDC tokens for that repo, any branch), so Terraform
  runs there as that role, including reading and writing the state. Personal SSO roles cannot
  assume it.
- **Permissions boundary:** every IAM role created here must set
  `permissions_boundary = local.permissions_boundary`, or the deployer role cannot create it.
- **Tags:** `project`, `owner`, `pillar` and `deployment` are added to every resource by the
  provider.
- **Network:** an existing VPC with three private subnets (services, databases) and two public
  ones (load balancers).

The files hold identifiers only (account id, ARNs, resource ids), never credentials.

## Secrets

`MCP_AUTH_TOKEN` and `SESSION_SECRET` are generated by Terraform as ephemeral values and written
to Parameter Store with write-only arguments, so they never appear in the Terraform state or plan.
To generate new ones, raise `secrets_version` in `secrets.tf` (a new `SESSION_SECRET` signs
everyone out).

`OPENROUTER_API_KEY` starts as a placeholder (`not-set`), which Terraform never overwrites. Set
the real key once, from your machine with the sandbox SSO profile; it never touches the repo or
GitHub:

```sh
aws ssm put-parameter --overwrite --type SecureString \
  --name /health-mcp/rag/OPENROUTER_API_KEY --value "$(read -rs -p 'Key: ' k; echo "$k")"
```

## The server

A `t4g.small` (2 vCPU, 2 GB, about $12 a month) with a 2 GB swap file, in a private subnet. Only
CloudFront reaches it, on the web port (see [The public URL](#the-public-url)); it reaches ECR,
Parameter Store and OpenRouter through the VPC's NAT, and admins reach it through SSM Session
Manager, never SSH. Its IAM role may only use SSM, pull its own images and read its own secrets.

- **Boot** (`server/user-data.sh.tftpl`): installs Docker and the Compose plugin (checked against
  its published checksum), adds swap, formats the data disk on first use and mounts it at
  `/srv/health-mcp/data`, and enables `health-mcp.service`, which runs `deploy.sh` on every boot
  once a rollout has written it.
- **App files:** `server/compose.yml.tftpl` and `server/deploy.sh.tftpl` are rendered by Terraform
  and written to `/srv/health-mcp/` by each rollout, so changing them does not replace the server.
- **`deploy.sh [commit]`**: reads the secrets from Parameter Store into `app.env` (root only),
  logs in to ECR, pulls the images, runs the database migrations, starts the containers and waits
  until they are healthy. The deploy workflow runs it through SSM with the commit it just pushed.
- **Data:** the SQLite database and imaging files live on their own encrypted disk, so a new
  instance (after a change to the boot script) finds them again.

Measured locally with the same images: about 355 MB for the three containers when idle, 625 MB
once the embedding model is loaded in the api and the MCP server, and about 550 MB more for the
reranker in the MCP server; hence 2 GB rather than a 1 GB `t4g.micro` ($6 a month).

### Adding a user

From your machine, with the sandbox SSO profile and the Session Manager plugin
(`brew install --cask session-manager-plugin`):

```sh
export AWS_PROFILE=health-mcp-sandbox
aws ssm start-session --target <server_instance_id>   # from the Deploy run's Terraform output
sudo docker compose -f /srv/health-mcp/compose.yml exec api \
  node apps/api/dist/cli/users.js add you@example.com --first Your --last Name
```

It asks for the password twice without showing it, and checks it against the password rules.
`password`, `remove`, `assign` and `list` work the same way (see the main README's Sign-in
section). Doctors can also sign up themselves at the app's URL (`/register`).

Patients created before they had owners (or whose doctor was removed) are seen by no one; give
them to a doctor with:

```sh
sudo docker compose -f /srv/health-mcp/compose.yml exec api \
  node apps/api/dist/cli/users.js assign you@example.com
```

## The public URL

The `app_url` output (also in the Deploy run's summary): `https://<id>.cloudfront.net`, with
CloudFront's certificate, so no domain is needed. It is also the app's `WEB_ORIGIN`, which marks
the session cookie `Secure`.

- **VPC origin:** CloudFront reaches the server privately inside the VPC (plain HTTP on port 3000
  there; viewers always get HTTPS). The server has no public IP, and its security group lets in
  only CloudFront's origin-facing addresses (the `com.amazonaws.global.cloudfront.origin-facing`
  prefix list).
- **No caching** of pages or API calls: everything is per user and behind sign-in, and all viewer
  headers, cookies and query strings reach the app. Only Next.js build assets
  (`/_next/static/*`, named by content hash) are cached.
- **Security headers** from AWS's managed policy: HSTS, `X-Content-Type-Options`,
  `X-Frame-Options`, `Referrer-Policy`.
- **Cost:** VPC origins are free; CloudFront's free tier covers 1 TB and 10 million requests a
  month. `PriceClass_100` uses the North American and European edges only.
- **Replacing the server** (only a change to the boot script does that): CloudFront cannot move a
  VPC origin to another instance while it is in use, so Terraform creates the new server and a new
  VPC origin first, moves the distribution to it, then deletes the old ones. The site is down
  from when the old server stops (to hand over the data disk) until the distribution has moved,
  about 20 minutes.

Creating the VPC origin and the distribution takes up to 15 minutes each.

## RAG monitoring (Phoenix)

[Phoenix](../docs/rag.md#monitoring-with-phoenix) shows each search and indexing run with its
passages, scores and timings. It runs on the server but is **off by default**: it needs about 730 MB
of memory, and the server has 2 GB. Start it when you want to look, stop it after; only searches
made while it runs are traced (the api and the MCP server always send their traces to it, and drop
them while it is off).

```sh
export AWS_PROFILE=health-mcp-sandbox
aws ssm start-session --target <server_instance_id>
sudo /srv/health-mcp/monitoring.sh start    # or stop, or status (with memory use)
```

It has its own URL, the `phoenix_url` output (also in the Deploy run's summary): a second CloudFront
distribution to port 6006 through its own VPC origin, open to CloudFront only like the app (Phoenix
serves from `/` only, so it cannot share the app's URL under a path). While Phoenix is stopped that
URL answers with an error.

**Sign-in:** Phoenix's login is on. Sign in as `admin@localhost` with the generated initial
password, then change it in Phoenix (its strong password policy is on, and it locks an account after
repeated failures):

```sh
aws ssm get-parameter --with-decryption --query Parameter.Value --output text \
  --name /health-mcp/rag/phoenix/PHOENIX_DEFAULT_ADMIN_INITIAL_PASSWORD
```

The initial password only applies to a new Phoenix database; after a change in Phoenix, that one
counts. Traces need `PHOENIX_API_KEY` (Phoenix's admin secret), which the api and the MCP server
read from `app.env`; Phoenix's own secrets are under `/health-mcp/rag/phoenix/`, which `deploy.sh`
writes to `phoenix.env` only. Traces are kept 14 days, on the data disk
(`/srv/health-mcp/data/phoenix`), and a deploy keeps Phoenix running (and updates it) when it was
started. Traces carry the patients' text: synthetic data only, as everywhere.

## Usage

`.github/workflows/deploy.yml` deploys `main` on every push to that branch, or by hand
from the Actions tab ("Deploy" → "Run workflow"). It runs only in `factoredai/health-mcp`, so
pushes to personal copies skip it.

1. **Terraform:** logs in as the deployer role with GitHub's OIDC token (no stored AWS keys),
   selects the `rag` workspace, plans (the end of the plan goes to the run's summary) and applies.
2. **Images:** builds the api, MCP server and web images for ARM (the server is a Graviton
   instance; GitHub's x86 runners emulate ARM with QEMU) and pushes each to its ECR repository,
   tagged with the commit and `latest`. Each image's build cache is kept in GitHub's cache.
3. **Rollout:** waits until the server is reachable through SSM, writes the Compose file and
   `deploy.sh` that Terraform rendered, then runs `deploy.sh <commit>` there and shows its output;
   the run fails if the deploy does.

Locally, without AWS access, you can check the configuration:

```sh
cd infra
terraform fmt -check -recursive
terraform init -backend=false && terraform validate
```
